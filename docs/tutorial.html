WSM helps an external teacher test numerical changes to a neural network. The run compares development results and preserves the selected checkpoint and its evidence.

Begin with 3 + (−1). The answer should be 2. The initial network in this repository returns 0. Its wiring already contains useful structure, but its output weights are both zero.

This tutorial follows the repository’s synthetic signed-addition example. Its teacher is a script containing three proposals, not a live AI model.

A network is a calculation with adjustable numbers

A weight multiplies a value. A bias adds an offset. An affine layer combines those operations. A neural network connects layers; here the graph stays fixed while numerical coefficients can change.

(x, y) → (x + y, −x − y)
→ (ReLU(x + y), ReLU(−x − y))
→ w₊ · h₊ + w₋ · h₋ + b

ReLU(z) = max(0, z). It keeps positive values and clips negative ones to zero. The first hidden unit carries the positive part of the sum. The second carries the magnitude of its negative part. Their weights are fixed here at [1, 1, −1, −1], with zero biases.

For (3, −1), the hidden affine values are (2, −2); ReLU gives (2, 0). Initially the output is 0 × 2 + 0 × 0 + 0 = 0. With output weights [1, −1], it becomes 1 × 2 − 1 × 0 = 2.

For (−3, 1), ReLU instead gives (0, 2). The same edited weights produce 0 − 2 = −2. The negative branch is why this works for signed inputs.

A residual is the prediction error. The SDK scales it as (prediction − target) / max(1, |target|). Loss is half the mean of squared scaled residuals, across every output and example. Smaller is better. The table uses only public development data.

Three proposals, one retained improvement

The scripted teacher names individual tensor entries and supplies replacement values. Each proposal is based on the current incumbent, the best checkpoint retained so far. Rejection leaves that incumbent unchanged.

StepCandidate [w₊, w₋, b]Development lossRecorded decision

The first proposal changes output.weight[0] to −1. On positive sums it reverses the sign, so it loses. The second proposal starts from the unchanged incumbent and replaces both output weights with [1, −1]. All public examples become exact. The last proposal starts from that accepted checkpoint and adds bias 1. Every answer shifts upward, so it loses.

Selection compares (development.loss, train.loss) lexicographically. Development loss decides first; training loss breaks an exact tie. A tie on both keeps the incumbent. Each valid candidate is evaluated separately before the run changes state.

Who owns each part?

The teacher proposes numbers

An external program receives a copied observation and returns explicit tensor replacements. Here it is the offline teacher-proposals.json fixture. No model is called.

The binary64 backend computes

wsm.binary64 owns coefficient access, checkpoint identity, patch materialization, and affine/ReLU predictions. The target is the fixed network being edited.

The run owns evidence and selection

SearchRun owns candidate attempts and history. It checks result bindings and compares the configured metric paths. It never interprets numerical example arrays.

The evaluator supplies feedback

NumericalEvaluation uses copied public examples. HarborEvaluation runs trusted grading through Verifiers in Docker. Native rewards and failure details remain separate from selection decisions.

Harbor owns execution

The upstream adapter stages the declared JSON in a fresh verifier, runs trusted tests, captures native output before teardown, and cleans up. The agent image contains the SDK and public problem.

Trusted task code owns correctness

A development package chooses public training and development examples. A separate final package chooses heldout examples and accepts a frozen run. Submission fields cannot choose a split.

Prompting changes a model's input. Gradient-based training computes derivatives. This example accepts explicit numerical replacements. It has no gradients, optimizer, model backend, hosted service, or GPU.

Final scores arrive only after finish() closes the run. Using final scores to choose another proposal would contaminate final evaluation. An unrestricted local teacher process can read host files; the library alone does not provide a sandbox.

The teacher exchange is ordinary JSON

The teacher receives exactly the copied object returned by run.inspect(). It includes the incumbent checkpoint, evaluator configuration and public feedback data, policy, remaining attempt information, baseline evidence, and event history. At construction, baseline is null. No evaluation has run yet.

teacher_send = json.dumps(run.inspect(), allow_nan=False)
print(teacher_send)  # Your transport sends these exact bytes to your teacher.
# The offline teacher returns the proposal below.

Run the same loop in Python

From the repository root, use Python 3.12 or later. The core SDK has no runtime dependencies.

python3 -m venv .venv
.venv/bin/python -m pip install -e packages/python
.venv/bin/python examples/demo.py --output /tmp/weightless-run.json

The demo prints not_improved, improved, then not_improved. Save this complete caller as /tmp/weightless-exercise.py and run it from the repository root with .venv/bin/python /tmp/weightless-exercise.py.

import json
from wsm import MetricPolicy, NumericalEvaluation, SearchRun, replay
from wsm.binary64 import create_checkpoint, predict

with open("fixtures/addition.json") as file:
    fixture = json.load(file)
initial = create_checkpoint(fixture["graph"], fixture["tensors"])
policy = MetricPolicy(("development.loss", "minimize"),
                      ("train.loss", "minimize"))
run = SearchRun(initial, evaluator=NumericalEvaluation(fixture["task"]),
                policy=policy, budget=8)
assert predict(initial, [3, -1]) == [0]

with open("examples/teacher-proposals.json") as file:
    proposals = json.load(file)
for teacher_reply in proposals:
    observation = run.inspect()
    proposal = dict(teacher_reply, base=observation["checkpoint"]["id"])
    decision = run.submit(proposal)
    print(decision["reason"])

frozen = run.finish()
restored = replay(frozen)
assert predict(restored, [3, -1]) == [2]
assert predict(restored, [-3, 1]) == [-2]
with open("/tmp/weightless-exercise.json", "w") as file:
    json.dump(frozen, file, indent=2)

submit composes the same public stages available for explicit execution control. On a fresh run using the variables above, the following builds, evaluates, and selects one candidate:

staged = SearchRun(initial, evaluator=NumericalEvaluation(fixture["task"]),
                   policy=policy, budget=8)
proposal = {
    "base": staged.inspect()["checkpoint"]["id"],
    "author": "scripted-teacher",
    "edits": [
        {"tensor": "output.weight", "index": 0, "value": 1},
        {"tensor": "output.weight", "index": 1, "value": -1},
    ],
}
candidate = staged.propose(proposal)
feedback = staged.evaluate(candidate)
decision = staged.select(candidate, feedback)
assert decision["accepted"]

Each valid proposal spends one attempt and permits one evaluation. Invalid or stale proposals spend nothing. Only one candidate can be pending. The first candidate evaluation retains a baseline once. Failed baseline evidence stays inspectable and prevents selection. No failure triggers retry or repair.

A valid native reward of zero is completed feedback. Infrastructure failure, malformed output, and task execution failure have distinct statuses and cannot win. finish() closes the run without evaluating pending work and returns copies of the same frozen contents.

Replace the evaluator with Harbor

The same teacher and selection policy can use native Docker grading. Install the optional integration packages, prepare separate trusted tasks, and build the image:

.venv/bin/python -m pip install -e 'packages/python[integration]'
.venv/bin/python scripts/prepare_harbor.py --development /tmp/weightless-development
docker build -t weightless-signed-addition:local examples/harbor/signed-addition/environment

Continue with the initial checkpoint, policy, fixture, and proposals from the caller above. Resolve the image explicitly, then use the native evaluator in the same loop:

from wsm.harbor import HarborEvaluation, resolve_image

image = resolve_image("weightless-signed-addition:local")
evaluator = HarborEvaluation(task_dir="/tmp/weightless-development", image=image)
run = SearchRun(initial, evaluator=evaluator, policy=policy, budget=8)
for teacher_reply in proposals:
    proposal = dict(teacher_reply, base=run.inspect()["checkpoint"]["id"])
    decision = run.submit(proposal)
    print(decision["reason"])
frozen = run.finish()

final = HarborEvaluation(task_dir="examples/harbor/signed-addition", image=image)
final_result = final.grade(frozen)
assert final_result["native"]["reward"] == {"reward": 1.0}

Development submits one candidate checkpoint, never an unfinished run. The final evaluator independently accepts the frozen run and scores heldout inputs. The trusted packages choose their split. Every result binds the run, attempt, checkpoint, configuration, and purpose. Native reward, numerical metrics, diagnostics, exit code, stdout, and stderr remain available.

The adapter invokes installed Verifiers HarborTask and isolated grade_task with zero retries. Its callback captures native diagnostics before teardown. It runs synchronously outside an active event loop. No teacher-model rollout is needed.

Replay reconstructs weights without grading again

replay(frozen) validates patches, budget use, result bindings, policy decisions, and the selected checkpoint. It applies patches and compares recorded metrics. It never runs the numerical evaluator, Docker, or a teacher. A dependency-free wheel can replay Harbor-produced runs.

Checkpoint v1 identity bytes are unchanged. Frozen runs use v2 because their evidence and replay contract changed. Deep copies protect nested caller data, and content hashes detect inconsistent changes.

An author can rewrite an entirely self-consistent unsigned history and recompute every hash. Replay does not authenticate external scores, prove that a teacher acted live, or promise repeatable external evaluation. Independent heldout grading checks the selected network's behavior.

What the checks establish

The implementation has local unit, schema, trusted verifier, and installed-wheel checks. The new adapter also ran real Docker development evaluations with native rewards zero, one, zero and the unchanged reject, accept, reject decisions. Independent final grading returned native reward one. The native Harbor CLI oracle also returned one. See docs/verification.md for reproducible commands and evidence boundaries.

The proposals are deliberately scripted. These results do not establish an AI teacher's discovery ability, a paper result, a general optimizer advantage, a Neutrino result, or a benchmark score. Broader models and model calls remain separate work.

Check your understanding

Why does the initial network return zero even though its hidden layer computes useful values?

Both output weights and the output bias are zero. The final layer discards the hidden values.

Does the second proposal build on the rejected −1 weight?

No. Rejection preserved the initial incumbent. Each proposal must name the current incumbent’s identity.

Why does [1, −1] handle negative sums?

For a negative sum, the positive branch is zero and the negative branch carries its magnitude. Multiplying that magnitude by −1 restores the sign.

Can you use held-out scores to choose the next proposal?

That would contaminate final evaluation. Active selection uses public development loss, then training loss.
